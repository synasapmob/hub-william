# Tools and contributors

Tools are folders of text files under `contributors/<owner>/tools/<tool-id>/`. The frontend bundles them at build time, lists them on the Tools page, and publishes the original files and one ZIP per tool under `/catalog/`. A few tools ship a standalone script (installer, downloader, terminal browser, job crawler) that runs on the user's computer, and two have a page in the browser or a relay in the API. TEXT TO AUDIO and AUDIO TO TEXT are described in [speech.md](./speech.md).

## Catalogue discovery

`apps/frontend/src/services/catalog/` builds the catalogue from the files themselves.

- **Sources.** `catalog-service.ts` imports every file matching `contributors/*/tools/**/*` with an eager `?raw` glob, so each file in a tool folder is bundled into the frontend as text. Tool folders therefore hold text files of modest size.
- **Which path is a tool file.** `collectionIdForPath` in `catalog-collections.ts` accepts `contributors/<owner>/tools/<id>/<file…>` with at least five path segments. It rejects `default/installer`, `default/mcp` and `synasapmob/installer`. The tool id is the fourth segment.
- **Owner.** The `default` folder maps to contributor `null` (the shared catalogue). Every other folder name is a contributor and is expected to be a GitHub login.
- **File title and description.** For Markdown, the title is the first `# ` heading (the file name when there is none) and the description is the first prose paragraph after front matter and the heading, skipping headings, tables, code fences, lists and blocks starting with inline code (`Tool documentation.` when nothing qualifies). For any other file, the leading `#` comment of the script gives the title (first line) and the description (first paragraph), with `Source file.` as the fallback. Sources are never rewritten and Markdown is never rendered to HTML.
- **Skill folders.** A folder containing `SKILL.md` is listed by that file alone. Its `LICENSE`, `README.md` and `references/` stay in the ZIP and at their published URLs but are not listed.
- **Presentation.** `COLLECTION_PRESENTATION` maps each of the nine ids in `TOOL_IDS` to a label and summary, and `TOOL_IDS` fixes their order. An unknown id gets a derived label (the id with `-` and `_` turned into spaces, first letter capitalised), the summary `Documents collected around <label in lower case>.`, and sorts after the known ids alphabetically. The same table is keyed by id, so a contributor who reuses an id such as `memory` or `skills` inherits that id's label, summary and sheet.
- **Counts.** A card shows the number of listed files. The toolbar counts `.md` files only.
- **URLs.** Each file's URL is `<origin><BASE_URL>catalog/<repo path>`. The origin is `window.location.origin` in the browser and `https://hub-william.site` when prerendering. A collection's archive is `catalog/collections/<owner|default>/tools/<id>.zip`.

## Tools page

`/tools` shows the shared catalogue and `/tools/<contributor>` shows one contributor's tools (`apps/frontend/src/routes/_app.tools.($contributor)/`).

- A **Catalogue** popover lists the contributors that have at least one tool, with a search field and the avatar `https://github.com/<login>.png`; the initial is the fallback.
- The toolbar search is component state, not part of the URL. `matchesCollectionQuery` matches the query against the collection label and summary and against every file's path, title and description. It does not search file contents.
- Selecting a card sets `?node=<tool-id>` and opens a sheet. The parameter is read only after hydration, so the prerendered page and the first client render agree. `findCollection` lowercases the id.
- Every sheet has an Introduction (the summary), the file list with a **Download all** link to the ZIP, and a link to the repository. Further sections depend on the tool:

| Tool                              | Extra section                                                |
| --------------------------------- | ------------------------------------------------------------ |
| `gateway`, `opencode`, `omp`      | Install commands (and, for `gateway`, the config they write) |
| `skills`, `link-skills`, `memory` | Install or run command                                       |
| `download-reel`                   | Usage command and the fetch-and-preview form                 |
| `edge-tts`                        | Usage command and the live generator                         |
| `vosk`                            | The in-browser recorder                                      |

- Install commands use the site origin and `VITE_API_BASE_URL` (`apps/frontend/src/utils/utils.gateway-config.ts`).
- Prerendering covers `/tools` and `/tools/<owner>` for every owner other than `default` that has at least one `.md` tool document (`apps/frontend/react-router.config.ts`).

## Publishing under `/catalog/`

`apps/frontend/scripts/vite/catalog-endpoint.ts` is a Vite plugin with `apply: "build"`, so `pnpm dev` does not serve `/catalog/`. It skips the SSR environment and dotfiles, walks `contributors/*/tools/` with owners sorted, and emits:

| Output                                       | Content                                                                                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `catalog/<repo path>`                        | Each tool file, byte for byte (for example `catalog/contributors/default/tools/gateway/gateway.md`)                                                     |
| `catalog/collections/<owner>/tools/<id>.zip` | Every file of the tool folder (including files the UI does not list), keyed by repository path, level 9, mtime 1980-01-01 so archives are deterministic |
| `catalog/index.json`                         | `description`, `repository`, `count`, `documents[]` (`id`, `path`, `url`, `bytes`) and `collections[]` (`id`, `path`, `url`, `bytes`, `files`)          |

URLs in `index.json` are prefixed with `VITE_BASE_PATH` (default `/`).

nginx (`infra/nginx/default.conf.template`) serves `/catalog/*.md` as `text/markdown` and `/catalog/*.sh|py` as `text/plain`, both UTF-8, because nginx has no mapping for these extensions and browsers would download them. Other files under `/catalog/` are served as-is on the site origin with nginx's default types. `curl` is unaffected either way. `apps/frontend/scripts/installers/tests/test_gateway_proxy.py` pins these rules.

## Contribution policy

`.github/workflows/contribution-policy.yml` runs on `pull_request_target` from the base branch and never checks out PR code. For a PR whose author is not the repository owner it requires:

- base branch `dev`;
- an unchanged head SHA during validation and a complete file list;
- every changed path (and every `previous_filename` of a rename) of the form `contributors/<author login, lowercase>/tools/<tool>/…/<name>.md`, with `<tool>` matching `^[a-z0-9][a-z0-9-]*$`, at least five segments, and path parts matching `^[A-Za-z0-9][A-Za-z0-9._-]*$`;
- file status `added`, `modified`, `removed` or `renamed`;
- every added or changed blob in the PR's tree to be mode `100644`, which rejects symlinks and executables.

The owner is exempt. Community PRs can therefore only add Markdown inside their own login's folder, so `contributors/default/` and every script, HTML file or installer are owner-only. Nothing checks the name of a tool's entry document. Files under `/catalog/` are served as-is from the site origin, and community contributions are limited to ordinary, non-executable Markdown files.

## Installers

`gateway.py`, `opencode.py` and `omp.py` configure local coding agents to use a Hub gateway key. They use only the Python standard library and run as `curl -fsSL <site>/<name>.py | python3 - --url=<api url>`.

Shared behaviour:

- **Inputs.** `--url` (or the `HUB_WILLIAM_GATEWAY_URL` environment variable) must be HTTPS, or HTTP on `localhost` or `127.0.0.1`. `--key` is the gateway key; without it a hidden prompt (`getpass` on `/dev/tty`) asks for it. A key needs at least 8 characters and no whitespace. The gateway key is created on the Agents page (see [gateway.md](./gateway.md)).
- **Writes.** Each file is written to a temporary file in the same folder, `fsync`ed, set to `0600` and moved into place with `os.replace`. The first time an installer overwrites a file it copies it to `<file>.hub-william.bak` (`0600`) unless that backup exists. New folders are created `0700`. An installer refuses to overwrite a config file that is a symlink to an existing file (the OpenCode plugin file `remember-model.mjs` is not checked).
- **Generated block.** The `# provider-catalogue: begin (generated)` … `end` region of each script is produced from the provider catalogue by `pnpm catalogue:generate` ([provider-catalogue.md](../provider-catalogue.md)).

| Installer     | Needs a TTY                            | Writes                                                                                                                               |
| ------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `gateway.py`  | Always (`/dev/tty`, even with `--key`) | Only the agents selected in an interactive picker (all four preselected); see below                                                  |
| `opencode.py` | Only when `--key` is absent            | `~/.config/opencode/opencode.json` and the plugin `~/.config/opencode/plugins/remember-model.mjs`                                    |
| `omp.py`      | Only when `--key` is absent            | The managed region of `~/.omp/agent/models.yml` (or `models.yaml` when only that exists; `PI_CODING_AGENT_DIR` overrides the folder) |

`gateway.py` targets, where `<url>` is the `--url` value:

| Agent       | File                                      | Written                                                                                                                                                                                            |
| ----------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Codex       | `~/.codex/config.toml`                    | `model_provider = "hub-william"` and the table `model_providers.hub-william` (`base_url` `<url>/gateway/openai/v1`, bearer token, `wire_api = "responses"`)                                        |
| Claude Code | `~/.claude/settings.json`                 | `env.ANTHROPIC_BASE_URL` = `<url>/gateway/claude`, `env.ANTHROPIC_AUTH_TOKEN` = the key                                                                                                            |
| AGY         | `~/.gemini/antigravity-cli/settings.json` | `modelProvider = "gemini"`, plus a marked block in `~/.zshrc`, `~/.bashrc` or `~/.profile` (chosen from `$SHELL`) exporting `GOOGLE_GEMINI_BASE_URL` = `<url>/gateway/gemini` and `GEMINI_API_KEY` |
| Grok        | `~/.grok/config.toml`                     | `[endpoints] models_base_url` and `[model.grok-build]` with `base_url` = `<url>/gateway/grok/v1` and the key                                                                                       |

DeepSeek and Groq have no native CLI here; they are reachable through OpenCode and OMP.

`opencode.py` and `omp.py` discover models before writing:

- For each provider in the catalogue they call `GET <url><models_path>` with `Authorization: Bearer <key>` and a 12 s timeout.
- A `401` with code `invalid_gateway_key` aborts with an invalid-or-revoked message. Any other failure counts as an empty list for that provider.
- If every provider is empty the installer aborts with "no provider models could be discovered" and writes nothing.

OpenCode specifics: the managed provider ids are `hub-codex`, `hub-claude`, `hub-gemini`, `hub-grok`, `hub-deepseek` and `hub-groq`. They are deleted and rebuilt on each run, and a provider with no models is left out. `opencode` is added to `disabled_providers`. `model`, `small_model` and per-agent models that point at a missing managed model are dropped. When no `model` is set, the first provider of `opencode_default_providers` (ChatGPT, then Claude) that was installed supplies one, preferring its `preferred_models`. Reasoning-effort metadata for ChatGPT models comes from the local `codex app-server` when `codex` is on `PATH`, with the catalogue as fallback. The `remember-model.mjs` plugin rewrites `opencode.json` when the user switches model.

OMP specifics: providers are rendered between the lines `  # hub-william: providers begin` and `  # hub-william: providers end` inside the root `providers:` mapping. The installer refuses a malformed or ambiguous marker pair, markers outside `providers:`, more than one root `providers:`, a same-name provider defined outside the markers, and a `models.json` that OMP has not migrated.

## DOWNLOAD REEL

**Script** (`apps/frontend/public/download-reel.sh`): a Bash wrapper that runs an inline Python 3 program.

- Arguments: `--platform` (`tiktok`, `facebook`, `x` or `twitter`), the link as `--url` or a positional URL (otherwise it prompts on `/dev/tty`), and `--output-dir` (default `~/Downloads`).
- The link must be HTTPS without credentials, on port 443, on the platform's host, and a single-video shape (TikTok `/@user/video/<id>`, `vm.`/`vt.tiktok.com/<code>` or `/t/<code>`; X `/status/<id>`; Facebook reel, video, `watch?v=`, `fb.watch/<code>` or `/share/r|v/<code>`).
- yt-dlp is used when it is on `PATH` or importable, with `--ignore-config --no-playlist --no-overwrites --restrict-filenames` and a combined video-and-audio format (MP4 preferred), so ffmpeg is not required. TikTok requires yt-dlp. Facebook and X fall back to public extractors (Facebook's embed page, `api.fxtwitter.com` for X) when yt-dlp is missing or fails.
- A fallback download goes to a `.part` file, must start with an MP4 `ftyp` marker and match `Content-Length`, and is published with `os.link`, so it never replaces another file. Browser cookies are never read.

**API relay** (`apps/api/src/api/reel/`, logic in `apps/api/src/api/reel/resolver.rs`; public, rate limited per IP):

| Endpoint                            | Limit                               | Purpose                                                                            |
| ----------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------- |
| `POST /reel/resolve`                | 30 per minute                       | Turns a public link into direct media URLs (`ResolvedVideo`, with `VideoVariant`s) |
| `GET /reel/stream?url=`             | 30 per minute, shared with download | Relays the bytes inline                                                            |
| `GET /reel/download?url=&filename=` | 30 per minute, shared with stream   | Relays the bytes as an attachment                                                  |

- The platform comes from the request or from the link's host. Resolution uses `api.fxtwitter.com` (X), `www.tikwm.com/api/` (TikTok) and Facebook's `plugins/video.php` embed, whose JSON strings are read as data and never evaluated.
- The relay opens only HTTPS URLs on `fbcdn.net`, `twimg.com`, `tiktokcdn.com`, `tiktokcdn-us.com` or `tikwm.com`, adds the matching `Referer`, forwards `Range` and passes `206` and `Content-Range` back with `Cache-Control: no-store`. Redirects follow at most 5 hops and only to platform, media or `fxtwitter.com` hosts.
- Limits: 8 concurrent relays (`503` when all are busy), 256 MiB per video, 8 MiB per fetched page or API reply, 20 s resolve timeout; relayed streams also use a 10 s connect timeout and a 30 s read (stall) timeout. Nothing is stored on the server.
- The Tools sheet (`tools-catalog-download-reel.tsx`) calls `/reel/resolve`, previews with `<video src="/reel/stream?url=…">` and downloads with `fetch` of `/reel/download` into a browser blob. The API relays every byte of the video; the poster image of the preview is loaded by the browser directly from the URL the resolver returns.

## Skills and Link skills

`skills` is a folder of agent skills and `rules/AGENTS.md`. The files are published as-is under `/catalog/`, and only the owner can publish scripts or HTML (see the policy above).

`link.sh` installs them into `~/.agents` (`AGENTS_HOME` overrides; `HUB_WILLIAM_ORIGIN` overrides the site):

- **Source.** Without `--path` it downloads `catalog/collections/synasapmob/tools/skills.zip` from the site. With `--path=<zip or folder>` it reads a local copy and fetches nothing.
- **Skills.** Each folder with a `SKILL.md` is copied to `~/.agents/skills/<name>`. A skill that differs from what is already there is moved to `~/.agents/.backups/<timestamp>/<name>` first; an identical one is skipped. The installed names go into the manifest `~/.agents/.hub-william-skills`. It refuses to run when `~/.agents/skills` is a symlink.
- **Rules.** `rules/AGENTS.md` becomes `~/.agents/AGENTS.md`. A file already at that path is replaced only while its SHA-256 equals the recorded hash in `~/.agents/.hub-william-rules` or a built-in hash of the first shipped copy, and the old file is backed up. A file the user edited, or a symlink, is kept and the new rules are saved as `~/.agents/AGENTS.hub-william.md`.
- **Links.** Only agents that do not read `~/.agents` themselves are linked, and only when their folder exists and nothing is at the link path: Claude Code (`~/.claude/skills/<name>`, `~/.claude/CLAUDE.md`), Codex (`~/.codex/AGENTS.md`) and agy (`~/.gemini/config/skills/<name>`, `~/.gemini/AGENTS.md`). It prints the `@` line to add to `CLAUDE.md` when that file is not the link.

`unlink.sh` reads the manifest, deletes only symlinks that point at the install, moves the installed skills to `~/.agents/.backups` and leaves the user's own skills and `~/.agents/AGENTS.md` alone.

## Memory

`contributors/synasapmob/tools/memory/memory.py` is a terminal browser (curses, Python 3.9 or newer, macOS or Linux) of what Claude Code, Codex, Grok and agy remember and are told. It imports only the standard library, makes no network request unless you set `VT_API_KEY` and answer yes, once per run, to the optional VirusTotal hash lookup of the disk tab (only the hashes of flagged files are sent), and writes only under the home folder (`--home` substitutes another), apart from a Linux Trash under `$XDG_DATA_HOME`. It reads link targets where they point.

- **Tabs.** `1 disk` is a read-only triage of files that look risky (see below), `2 memory` is the default and `3 rules` lists instruction files, the `.md` files in rule folders, and skills. `1`, `2`, `3` and `Tab` switch.
- **Sources.** The `AGENTS` and `RULES_AGENTS` tables hold the paths per agent. Memory covers Claude Code project memory folders, Codex `~/.codex/memories` and the `stage1_outputs` table of `~/.codex/memories_1.sqlite` (at most 500 rows), and Grok's memory-v2 topics and observations. The rules tab adds `~/.agents` and lists it first.
- **Viewer.** Right or Enter opens a folder or reads a file as text: at most the first 256 KiB, opened with `O_NOFOLLOW`. `p` pretty-prints `.json` and `.jsonl`.
- **Trash.** `d` previews what will move and asks `y/N` (default no). On the memory tab only learned memory can move; on the rules tab instruction files, rule files, skills and links can move. Generated indexes and SQLite databases never move, and file contents are never edited. `refusal()` re-checks the kind, the recorded folder, existence and symlinks before every move. The destination is `~/.Trash` on macOS and `$XDG_DATA_HOME/Trash/files` (default `~/.local/share`) with a `.trashinfo` record elsewhere. A failed move is never retried as a permanent delete.
- **Disk tab.** A read-only triage of where risky files usually land, shown in five groups with a label row for each (`WORKSPACE`, `APPLICATIONS`, `AGENTS`, `SHELL & STARTUP`, `TEMP`; a group with nothing in it has no label). `WORKSPACE` is `~/Documents`, `~/Downloads` and `~/Desktop`. `APPLICATIONS` is `~/Applications` and, for the account's own home, `/Applications`: each application (one folder down included) is one row with the size and the number of files inside its bundle, so the biggest are easy to see, and its signature is read with `codesign` (about 0.05 s each, at most 200 per scan). Checking a signature against the files takes about 2 s per application, so that waits for `r` (at most 60 s). `AGENTS` has one row per agent folder (`~/.claude`, `~/.codex`, `~/.gemini`, `~/.grok`, `~/.agents`: settings, hooks, commands, prompts and skills, never history) and one row per project the agents know, found from Claude's list of projects, with only its agent files (`CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `.claude/` settings, hooks and skills), never the rest of the repository. A project in a scratch folder outside the home is left out. `SHELL & STARTUP` is the shell startup files, `crontab -l`, and the LaunchAgents, autostart and systemd user units, plus the system LaunchAgents and LaunchDaemons for the account's own home. `TEMP` is `/tmp` and `/var/tmp`, also only for the account's own home. `~/Documents` is too big to read file by file (on one machine: over 2 million files and 86 GB, which takes about a minute to count), so it is counted by `stat` alone for 5 s, or 120 s after `r`, and shown with its 40 biggest files and up to 100 files with an odd name (a double extension, crack or keygen), which get the whole check. A count that stopped early is marked with a plus (`327k+`, `64.0 GB+`, also on the label and the totals) and opening the place says so. What was counted is kept for the session and made again on `r`. Inside a place `s` toggles biggest first and worst first. A label row carries the totals and the worst kind of its places, there is a blank line above each label (the first too, under the column heads), the cursor never stands on a label or on a blank line, and the totals line counts each place once. Inside a group the worst place comes first, and in a tie an agent comes before a project. Each place lists its files worst first with `FILES`, `SIZE`, `AGE` and a `KIND`: `ok`, `unknown`, `suspicious` or `maybe malware`. Right on a file shows the reasons, a path, the file type and the hash if it was computed, never the file's text, and a reason names the pattern and never the matched text. The tab never moves or deletes anything and never runs a file.
  - **Scoring.** Every finding is a signal of weight strong (3), medium (2), weak (1) or known. `judge()` calls a known finding or two strong signals `maybe malware` and a score of 3 or more `suspicious`, so one weak signal, such as a download flag or a name, never decides alone.
  - **Quick checks (each visit to the tab, and each place you open).** The name (a double extension, a risky kind, `crack` or `keygen`), the first 64 KB (what the bytes say a file is against what its name says, entropy, and script text such as `curl | sh`, base64 decode and run, a reverse shell, a miner pool, a fake password dialog, credential files with an upload), the place (a program in a temp folder), login items (a plist or unit that starts a program from a temp folder or Downloads), agent settings (an MCP server that runs an unpinned package or is handed a secret) and, on macOS, `codesign` and the download flag for programs and packages. Results are cached in memory by path, size and modification time. No more than 3000 files and 8 seconds per place and 40 signature checks per scan; links are not followed; names are cleaned of control characters before they reach the screen; XML plists are never given to an XML parser.
  - **Deeper checks (`r`).** A known-bad SHA-256 list (`--hashes FILE` or `MEMORY_BAD_HASHES`), YARA (`yara` on the path with `--rules FILE`, `MEMORY_YARA_RULES` or Apple's XProtect rules) and ClamAV (`clamscan`), each only if installed, and, only after a question answered once per run, VirusTotal for the hashes of flagged files (`VT_API_KEY`, only over https, at most 8 per scan, stopped by a busy answer). Only 64-character hashes are sent, never files or names. What they find is kept for the session and shown by later quick scans until the file changes. `--list --tab=disk --deep` and `--online` do the same without the interface.
  - **Limits.** It finds suspicious things, not viruses, and a clean result is not proof. It was checked against made-up files and on one machine; the VirusTotal answer shape and its limits were not checked against the live service.
- **Non-interactive.** `--list` prints the table and changes nothing (`--tab=memory|rules|disk`, `--agent` and `--home` refine it). Without a terminal the interactive screen exits with status 2.

## Job crawler

`contributors/synasapmob/tools/job-crawler/job-crawler.py` collects IT job listings from the boards ITviec, TopCV, CareerViet and Indeed and from the career pages of WorldQuant, Topicus Vietnam, Symbotic, Lecle Vietnam, Luce and Axon on the user's computer and runs as `curl -fsSL <site>/catalog/contributors/synasapmob/tools/job-crawler/job-crawler.py | python3 - --output-dir=<folder>`. The tool id is not in `TOOL_IDS`, so the Tools page derives the label (`Job crawler`) and summary and sorts it after the known tools. Its options and output are documented in `job-crawler.md`.

- **Setup.** The script imports only the standard library until it needs a browser. On the first run it installs Playwright with `pip install --target` into `~/.cache/hub-william/job-crawler/site` (`--cache-dir` overrides), because a script piped into `python3 -` cannot re-run itself in a virtual environment. It launches the user's Google Chrome through Playwright with its own persistent profile in the same folder and downloads Playwright's Chromium only when Chrome is missing (that path is untested). It never reads the user's browser profile, never signs in, and sends nothing to Hub William.
- **Sources.** Each site is a `Source` in `SOURCES`: the first list page, a CSS selector for one job card, a JavaScript function that returns one object per card, and one that returns the next page's address (followed only when it is HTTPS on the site's own host). ITviec takes the keyword in the address (`?query=`); TopCV's keyword is typed into its search box, because the address that box produces was only observed for one word. TopCV's list address keeps `?category_family=r257`: without it the same page answered 404 in testing. ITviec draws a job as `.job-card` in its list and as `.mini-job-card` on a company page, where the company's name is only in the page heading and a card has no posted age or work model. CareerViet (`careerviet.vn`, `.job-item`, 50 jobs a page) has no addresses behind its page buttons, but a page number in the list address works (`...-c1-vi.html`, `...-c1-trang-2-vi.html`), so its next-page script builds that address from the total in the page heading and stops at the last page. Without a keyword it reads the software IT category (`cntt-phan-mem-c1`, 441 jobs on 2026-11-27); a keyword uses `/viec-lam/<keyword>-k-vi.html`.
- **Filters.** `--company` and `--location` are case- and accent-insensitive substring matches on the company and location of each job (a comma means any of the values), applied before a job is counted; `report.json` records `filtered_out`. Where a site can find a company by name (`Source.company_search`: ITviec and CareerViet), each `--company` is its own search, and a name with no matching jobs is listed in `no_jobs_for` without failing the site. On ITviec, searching an exact company name redirects to that company's page with all its jobs (observed 2026-11-27: MB Bank, 23 jobs on one page); CareerViet's keyword search matched Vietcombank's own jobs. - **Role filter.** `--role` keeps a job when its title matches one of the roles. `squash()` removes everything but letters and digits from a role, and `role_patterns()` turns it into a whole-word pattern that allows one space, hyphen, underscore or slash between any two letters, so `Front-end`, `Frontend` and `Front end` are one role; `ROLE_ALSO` adds `Software Developer` and `Solutions Engineer`. `matches()` also keeps a job whose `role` group is the role (`ROLE_OF_TERM` maps the squashed term to its group), so `--role=Back-end` keeps `.NET Developer`, which never says Backend; `Developer` alone with no group is not a role. `Mobile` is special-cased (`_MOBILE_ROLE`): a mobile word (`mobile`, `android`, `ios`, `flutter`, `react native`) near `developer`, `engineer`, `dev`, `programmer` or `architect`, because plain `mobile` kept `Marketing (Mobile App)`, `UI/UX Designer – Mobile app` and `Mobile Robotics` on the real sites. Rows still carry `tags` and `scraped_at`, but neither is written to the sheet or the CSV: `tags` feeds `--keyword` on a company page.
- **Date filter.** `--date=N` (default 30, 0 means every date, at most 3650) is the one filter that is on by default. `read_posted()` returns the day a card's posted text names and whether it was edited; `normalize()` stores the day as `posted_on` (a `date`, or `None`; the key is not a CSV column) beside the `posted` text that `format_posted()` builds from the same call, so the filter and the sheet use the same, last, date. `posted_within()` keeps a job when `today - posted_on <= N` days, inclusive, and keeps a job with no `posted_on`, because nothing says it is old; `matches()` calls it first. The lists are not sorted by date, so every page is still read and old jobs are only dropped (they count in `filtered_out`). `report.json` has `date_days` and `jobs_without_a_date`. Checked on 2026-11-27 with the filters of the 187-job run: the default 30 days kept 178, every dated job was at most 30 days old (Topicus had one at exactly 30), and the 18 undated jobs were all on the WorldQuant (6), Symbotic (7) and Lecle (5) pages; all jobs on ITviec, TopCV and CareerViet had a date.
- **Dates and salary.** `format_posted()` turns whatever a page shows into `Created at DD-MM-YYYY`, or `Edited at DD-MM-YYYY` when the text says updated (`Cập nhật`): a numeric date (`27-11-2026`), an English one (`Nov 25, 2026`), or an age (`Posted 3 days ago`, `Đăng 1 tuần trước`), which is counted back from the time of the run (a month is 30 days), so it is approximate. Text it cannot read as a date, or a date that does not exist, is kept as written. `clean_salary()` drops a `Lương:` or `Salary:` label and leaves every other value (`Cạnh tranh`, `Thoả thuận`) alone. `format_experience()` shows experience as `4-5 years`, `4 years`, `5+ years`, `Under 1 year` or `Entry-level` (TopCV writes `2 năm`, `Trên 5 năm`, `Không yêu cầu`) and keeps text it cannot read. `short_location()` separates several places with a comma, never a semicolon, and drops a repeat. The Topicus reader takes the date out of a line that may hold only the date, because a card with no experience has no `•`.
- **Role groups.** `normalize()` adds `role`, one value from `ROLE_GROUPS`, to the row. It is the `role` column of the sheet and the CSV, written before `title`: a spreadsheet's filter list shows what a column holds, so the groups can only be listed from a column of their own, and the titles stay as the sites wrote them (the user first asked for no role column and for the `title` filter to list the groups, which one column cannot do, then asked for the groups in that filter again on 2026-11-27). It also orders the rows. It is decided by `role_group(title)` from the title alone with the same `role_patterns()` the `--role` filter uses: `Fullstack` first (the word, or both Backend and Frontend), then the mobile family through `_MOBILE_ROLE` (Android, iOS, Flutter, React Native or the word mobile, all `Mobile`), then `Backend`, `Frontend`, `Solution Engineer`, `Product Owner`, `Product Manager` and `Software Engineer`, and last a server stack word (`_BACKEND_STACK`: `.net`, `dotnet`, `asp.net`, `c#`, `java` but not `javascript`, `php`, `python`, `golang`, `node.js`, `ruby`, `rails`, `laravel`, `spring`, `django`) next to `developer`, `engineer`, `dev`, `programmer` or `lap trinh vien` (`_DEVELOPER`) is `Backend` when the title has none of the words in `_NOT_BACKEND` (data, machine learning, ml, ai, devops, qa, qc, test, security, embedded, firmware, sre, reliability, support, analyst, bi, etl, designer, sales, consultant, trainer, game, unity, blockchain, erp, odoo, automation, low-code; `_DEVELOPER` also takes the plurals), checked on the 1,305 jobs of 2026-11-27, where the first version also took a site reliability engineer, a Unity game developer, an automation engineer and ERP, low-code and blockchain developers, and missed `Senior .NET Developers`, which is how `.NET Developer` and `Senior Java Engineer` get there and `Data Engineer (Python)` and `QA Engineer (Java)` do not. `sort_jobs()` orders rows by `ROLE_GROUPS`, then company, then title, and `report.json` counts jobs per group in `role_groups`. A title with no group has an empty `role` and sorts last.
- **Location rule.** `matches()` looks for each `--location` word in the job's location and its work model, because ITviec shows `Remote` as a work model. `location_words()` treats `Ho Chi Minh City`, `HCM`, `HCMC` and `Saigon` as one place, so the sites' spellings (`Ho Chi Minh`, `Hồ Chí Minh (mới)`, `VNM Ho Chi Minh`, `Hanoi or Ho Chi Minh City, Vietnam`) all match. A country alone (`Vietnam`, on Luce) does not match a city. `short_location()` writes the `location` column with one spelling per place, because a spreadsheet's filter list shows what the cells hold and one entry per spelling is what the user saw (`HN, HCM` and `HCM, HN`, `Da Nang` and `Đà Nẵng`, 30 values for a handful of cities in a 1304-job run, 21 after): it splits the text on `; , / & |`, `-` and `or`/`and` (keeping `Bà Rịa - Vũng Tàu` and `Thừa Thiên Huế` whole), maps each part through `_PLACE_NAMES` (`HCM`, `HN`, and the 63 provinces of `VIETNAM_PLACES` as unaccented title case), drops `(mới)`, `N nơi khác`, `Others`, `Vietnam` and districts (`Quận 1`, `Q3`, `HCM Q1`, `District 7`, `Thủ Đức`), and writes the places as `HN`, `HCM`, `Da Nang`, then the rest from A to Z. A text with no Vietnamese place in it (`USA Remote & Travel`, `Singapore`, a bare `Vietnam`) is returned as it was. A job in several places is one combined value, so the filter list shows the combination, and the Excel filter's search box finds every value with `HN` in it. `normalize()` keeps the page's own text in `location_raw`, which `matches()` reads, so `HN` and `HCM` also work as filter words.

- **Real Chrome mode.** It is the default on macOS: `choose_browser()` (called by `main()` before anything opens) turns `options.my_chrome` on when the platform is `darwin`, `CHROME_PROGRAM` exists, and neither `--own-browser` nor `--headless` was given, so the `curl ... | python3 -` command needs no flag; `--my-chrome` only insists on it, and both together are an argument error. `parse_args()` leaves the choice alone, so the tests that call it behave the same on any platform, and `main()`'s Playwright tests pass `--own-browser`; `setUp` replaces `connect_real_chrome` with a function that fails, because a test that reached the real one on a Mac with Chrome hung and drove the developer's Chrome. Real Chrome mode replaces Playwright with `ChromeContext`, `ChromePage` and `ChromeBridge`, which give the crawler the few page actions it uses (`goto`, `locator().count()`, `evaluate`, `title`, `url`, `fill`, `press`, `wait_for_url`, `screenshot`, `close`) by running small AppleScripts against the user's Google Chrome (`osascript -`, the script on stdin and the arguments in `argv`). Chrome 136 and later ignore remote debugging on the default profile and a different profile uses a different encryption key, so the user's logins can only be reached this way, with `View > Developer > Allow JavaScript from Apple Events` turned on. Each site gets a new window; JavaScript runs only there; the window is closed after the site; Chrome is never quit. `goto` marks the old page with `window.__crawlerLeft` and waits for a new document that lacks it, and reads the HTTP status from `performance.getEntriesByType('navigation')[0].responseStatus`. `connect_real_chrome()` runs a test sum in a blank window first and says how to fix a missing setting or permission. A window is not photographed: `screenshot` writes the page's text next to where the picture would go. `ChromePage.ask` retries a request when Chrome says it cannot get the window but `exists window id` still answers true (a hiccup just after a window opens), so only a window that is really gone ends the run. - **Chrome profile.** `make new window` opens in the profile Chrome used last, and `browser.allow_javascript_apple_events` is saved per profile (`<profile>/Preferences`), so a run failed with "turned off" whenever the last-used profile was not the one with the setting on (13 profiles, 1 with it on, on 2026-11-27). `ChromeBridge.open_window()` therefore runs Chrome's own program with `--profile-directory=<profile> --new-window about:blank`, under a lock, and takes the id that was not in `id of every window` before; `--new-window` keeps it from becoming a tab of one of the user's own windows (`open -na` gave AppleScript errors -600 and -609 in 4 of 6 runs). The "turned off" message names the profile and `--chrome-profile`. The profile is found, not typed: `chrome_profiles_with_apple_events()` reads `~/Library/Application Support/Google/Chrome/<folder>/Preferences` for each folder except `System Profile` and `Guest Profile` and keeps those whose `browser.allow_javascript_apple_events` is `true` (the only value it reads), ordered by `Local State`'s `profile.last_used` then `profile.profiles_order`; the first becomes `options.chrome_profile` (`--chrome-profile` default is empty, and a named profile skips the search) and the choice is logged with the others that qualify. On 2026-11-27 it returned `Default` alone of 13 profiles, which is the profile the earlier runs used, and a run with no `--my-chrome` and no `--chrome-profile` logged `using your Chrome profile 'Default'` and read the same jobs. When none qualifies, `choose_browser()` exits with `NO_PROFILE_MESSAGE` (View -> Developer -> Allow JavaScript from Apple Events, then run again) before a window opens; the exit status is 1 like every `sys.exit(message)` here, and the exit-status text now says so. - **Quiet windows.** A person cannot work while windows open and close, so `--my-chrome` is quiet unless `--show-windows` is given. Measured on Chrome 158 on macOS on 2026-11-27: AppleScript's `set minimized` and `set visible` are accepted but read back unchanged (`minimized=false visible=true`), so they cannot hide a window; a window asked to sit at 6000,6000 is pulled back on screen, and a tall one is clamped vertically but may overhang the right edge; a 200 by 120 window reports `document.hidden` true and lays the page out for a narrow viewport, and CareerViet showed 0 job cards in it, while a 1300 by 700 window with only 32 pixels on screen reported `document.hidden` false, a 1300 by 579 viewport and 50 CareerViet job cards. `ChromeBridge.parked_bounds()` therefore keeps a normal-sized window and puts it so that a 32 pixel sliver sits at the right edge of the usable screen (read once from the first window with `screen.availWidth`, `availHeight` and `availTop`), created in one AppleScript (`open_at`) so it never shows at full size. `FOCUS_STEALERS` (`open`, `open_at`, `navigate`) record the front app with `lsappinfo` before and give it the focus back with `open <bundle path>` after, unless it is Chrome. A Cloudflare check calls `ChromePage.show()` (a usable size, then `activate`) and `hide()` when it clears (back to the parked place), so only the window that needs a click comes forward. The front app is recorded once for all windows that are forward together (`ChromeBridge.hold_focus()` and `release_focus()`, and `_focus` serialises `FOCUS_STEALERS`), because a window that recorded it after a sibling had come forward saw Chrome in front and gave Chrome the focus back. Chrome also takes the focus by itself 1 to 3 seconds after a page starts loading, after the handback: with the terminal in front for 2 seconds in a row, then a navigation, Chrome came forward 0.7 to 3 seconds later in 5 of 7 tries, through AppleScript's `set URL`, through `location.assign` in JavaScript, and when new tabs were opened in one parked window (those tabs did load, 50 CareerViet cards each, so tabs instead of windows would not stop it). `ChromeBridge.keeping_focus()` therefore also starts a watch thread (`FOCUS_WATCH_SECONDS` 4, polled every `FOCUS_WATCH_POLL` 0.3 s) that gives the focus back each time Chrome has just taken it, and does nothing when a command found the person in Chrome already, or while a window is forward for a check. A sampler of the front app cannot tell the tool from the person using Chrome: in three quiet runs Chrome was in front in 54%, 84% and (instrumented) 97% of the samples or commands, and the last number is mostly commands that began with Chrome already in front, so the effect of the watch is not measured. `crawl_pages_side_by_side()` keeps one window per worker thread (`threading.local`) for all its pages and closes them together at the end, so a run opens a few windows instead of one per page.
- **Reading at the same time.** With `--my-chrome` there are two levels, both using threads (each AppleScript call is its own `osascript` process, so they run side by side), and neither exists in the Playwright mode, whose synchronous API is not thread-safe. `collect_side_by_side()` reads up to `--sites-at-once` sites together, each in its own window, starting the first windows 2 seconds apart; one site failing does not stop the others. Within a site, `crawl_search()` reads page 1 first; `Source.total_pages` (a JavaScript reader: the heading's count over the page size for ITviec and CareerViet, `#job-listing-paginate-text` for TopCV) gives the page count, `page_template()` turns the address of page 2 (`?page=2` or `-trang-2-`) into the address of page N, and `crawl_pages_side_by_side()` reads pages 2 to N with up to `--pages-at-once` windows, each resting `--delay` between its pages. `jobs`, `seen` and a site's result are shared, so `record_rows()` and `fail_page()` take `_LOCK`; the first failure sets a `threading.Event` so no new page starts, and rows are sorted at the end, so the order pages finish in does not matter. A site that blocks the windows gets a second chance: `crawl_pages_side_by_side()` records the pages read in `done`, and when the first pass (`_read_pages()` with `--pages-at-once` windows) ends with the site `blocked` it waits `BLOCK_COOLDOWN` (60 s), resets the status, and reads the pages left with `RETRY_WINDOWS` (2) windows, once; a second block ends the site and keeps what was read. TopCV blocked 5 windows after 10 or 11 pages in two runs in a row on 2026-11-27 (after about ten full runs that day), a single window read 3 pages minutes later, and the next full run passed, so the block is temporary and rate-based; the retry itself was tested with a fake site, not yet seen live. A counted page that comes back `empty` is loaded once more before it fails the site: in the quiet run of 2026-11-27 CareerViet pages 8 and 9 showed no job cards (the saved page text had the header "441 việc làm" and no list), and page 8 held 50 job cards when opened again a few minutes later, in a parked window and in a normal one; the cause was not found. Not tried: a narrow phone width, dark mode, and keyboard use beyond what the tests do.
- **Output.** `<output-dir>/YYYY-MM-DD-HHMMSS/` holds `jobs.xlsx`, `jobs.csv` and `report.json`; a run that collected no jobs writes only `report.json` and any screenshots, so a header-only sheet is never left behind. Repeats are removed by the job's address without its query string. `jobs.xlsx` is a one-sheet workbook the tool writes itself with `zipfile` and no third-party library: each title is a hyperlink to the job, there is no url column, the header row is frozen with an autofilter, and every text cell is inline text, so nothing runs as a formula. `posted`, `experience` and `salary` are typed cells (see Sortable cells). Both files leave out the `source` column when every job's source equals its company (`visible_columns`: a run of career pages only). `jobs.csv` has the same jobs with a `url` column, as UTF-8 with a BOM, and prefixes cells that start with `=`, `+`, `-` or `@` with `'`. The workbook was read back with `openpyxl` in testing; it has not been opened in Excel, Numbers or Google Sheets by the author. ITviec's salary is empty for a visitor who is not signed in.
- **Observed on 2026-11-27.** A plain `curl` got 403 from both sites. One run read page 1 of each (20 ITviec jobs, 50 TopCV jobs), then met a human check on ITviec's page 2 and a block page on TopCV's page 2. A different network or browser may behave differently.

## Tests and CI

`apps/frontend/scripts/installers/tests/` holds the Python suite: `test_gateway_installer.py`, `test_opencode_installer.py`, `test_omp_installer.py`, `test_download_reel.py`, `test_link_skills.py`, `test_memory.py`, `test_job_crawler.py` (against a fake browser page, never the live sites) and `test_gateway_proxy.py` (the nginx contract above and the gateway and Playground body limits). It is not part of `pnpm test`.

- `tests/run.sh` runs the suite once per distinct Python version it finds, trying `/usr/bin/python3`, `python3.9` to `python3.14` and `python3` in that order.
- CI (`.github/workflows/trusted-ci.yml`, job `checks`) runs `python3 -m unittest discover -s tests -p 'test_*.py'` from `apps/frontend/scripts/installers`, and only for pull requests that the repository owner opened from a branch in this repository, or a manual dispatch.
- `.github/workflows/contribution-policy.yml` is the check for community pull requests, with its own test in `.github/scripts/contribution-policy.test.mjs`.
